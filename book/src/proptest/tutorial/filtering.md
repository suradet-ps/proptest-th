# การกรอง

บางครั้งคุณเจอกรณีที่ค่าอินพุตมีข้อจำกัด "ไม่ปกติ" บางอย่าง เช่น จำนวนเต็มต้องเป็นเลขคู่ หรือค่าสองค่าต้องไม่เท่ากัน

โดยทั่วไป ทางออกในอุดมคติคือหาวิธีรับค่าตั้งต้น แล้วใช้ `prop_map` แปลงมันเข้าสู่โดเมนที่ไม่ปกติที่ต้องการ ตัวอย่างเช่น การสร้างจำนวนเต็มคู่ ให้ใช้ประมาณนี้

```rust
# extern crate proptest;
use proptest::prelude::*;
prop_compose! {
    // Generate arbitrary integers up to half the maximum desired value,
    // then multiply them by 2, thus producing only even integers in the
    // desired range.
    fn even_integer(max: i32)(base in 0..max/2) -> i32 { base * 2 }
}
```

สำหรับกรณีที่ทำแบบนั้นไม่ได้ ก็สามารถกรองกลยุทธ์ได้ จริงๆ แล้ว Proptest แบ่งตัวกรองออกเป็นสองประเภท:

- ตัวกรองแบบ "โลคอล" (local) ใช้กับกลยุทธ์ตัวเดียว หากค่าหนึ่งถูกปฏิเสธ ค่าใหม่จะถูกดึงจากกลยุทธ์นั้นเพียงตัวเดียว

- ตัวกรองแบบ "โกลบอล" (global) ใช้กับกรณีทดสอบทั้งกรณี หากกรณีทดสอบถูกปฏิเสธ ทั้งหมดจะถูกสร้างใหม่

ความแตกต่างนี้ค่อนข้างเป็นไปตามอำเภอใจ เพราะตัวกรองแบบ "โกลบอล" นั้นสร้างได้เพียงแค่นำตัวกรองแบบ "โลคอล" มาครอบกลยุทธ์อินพุตทั้งชุด ในทางปฏิบัติ ความแตกต่างอยู่ที่ว่าโค้ดส่วนไหนเป็นผู้ปฏิเสธ

ตัวกรองแบบโลคอลสร้างขึ้นด้วยคอมบิเนเตอร์ `prop_filter` นอกจากฟังก์ชันที่บอกว่าควรยอมรับค่าหรือไม่แล้ว มันยังรับค่าชนิด `&'static str`, `String`, .. ซึ่งใช้บันทึกว่าการปฏิเสธเกิดขึ้นที่ไหน/เพราะอะไร

```rust
# extern crate proptest;
use proptest::prelude::*;

proptest! {
    #[test]
    # fn dummy(0..1) {} // Doctests don't build `#[test]` functions, so we need this
    fn some_test(
      v in (0..1000u32)
        .prop_filter("Values must not divisible by 7 xor 11",
                     |v| !((0 == v % 7) ^ (0 == v % 11)))
    ) {
        assert_eq!(0 == v % 7, 0 == v % 11);
    }
}
# fn main() { some_test(); }
```

การกรองแบบโกลบอลเกิดขึ้นเมื่อตัวเทสต์เองคืนค่า `Err(TestCaseError::Reject)` โดยมีมาโคร [`prop_assume!`](https://docs.rs/proptest/latest/proptest/macro.prop_assume.html) ที่ช่วยให้ทำเช่นนี้ได้ง่าย

```rust
# extern crate proptest;
use proptest::prelude::*;

fn frob(a: i32, b: i32) -> (i32, i32) {
    let d = (a - b).abs();
    (a / d, b / d)
}

proptest! {
    #[test]
    # fn dummy(0..1) {} // Doctests don't build `#[test]` functions, so we need this
    fn test_frob(a in -1000..1000, b in -1000..1000) {
        // Input illegal if a==b.
        // Equivalent to
        // if (a == b) { return Err(TestCaseError::Reject(...)); }
        prop_assume!(a != b);

        let (a2, b2) = frob(a, b);
        assert!(a2.abs() <= a.abs());
        assert!(b2.abs() <= b.abs());
    }
}
# fn main() { test_frob(); }
```

ถึงจะมีประโยชน์ แต่การกรองก็มีข้อเสียหลายอย่าง:

- เนื่องจากการกรองเป็นเพียงการสุ่มแบบปฏิเสธ มันจึงทำให้การสร้างกรณีทดสอบช้าลง เพราะต้องสร้างค่าเพิ่มเติมหลายรอบเพื่อให้ผ่านตัวกรอง ในกรณีที่ตัวกรองคืนค่าเท็จเสมอ ในทางทฤษฎีแล้วเทสต์อาจไม่สร้างผลลัพธ์ใดๆ ได้เลย

- Proptest ติดตามจำนวนการปฏิเสธแบบโลคอลและโกลบอลที่เกิดขึ้น และจะยกเลิกหากเกินจำนวนที่กำหนด วิธีนี้ป้องกันไม่ให้เทสต์ใช้เวลานานมากจนเกินไปเพราะการปฏิเสธ แต่ก็หมายความว่าไม่ใช่ตัวกรองทุกตัวจะใช้งานได้ในการตั้งค่าเริ่มต้น ขีดจำกัดของการปฏิเสธแบบโลคอลและโกลบอลนั้นต่างกัน โดยค่าเริ่มต้น proptest อนุญาตการปฏิเสธแบบโลคอลจำนวนมาก แต่จำกัดการปฏิเสธแบบโกลบอลไว้ค่อนข้างน้อย ด้วยเหตุผลว่าการปฏิเสธแบบแรกนั้นราคาถูกแต่อาจเกิดบ่อย (เพราะถูกสร้างมาในกลยุทธ์แล้ว) ส่วนแบบหลังนั้นราคาแพงแต่เกิดได้ยาก (เพราะเป็นกรณีขอบเขตของเทสต์นั้นๆ)

- การชริงก์และการกรองเข้ากันได้ไม่ดีนัก เมื่อชริงก์ หากค่าหนึ่งถูกปฏิเสธ ก็จะไม่มีข้อมูลผ่าน/ไม่ผ่านให้ชริงก์ต่อได้อย่างถูกต้อง แต่ proptest จะจัดการการปฏิเสธเช่นนั้นเหมือนกับการจัดการชริงก์ที่ทำให้เทสต์ผ่าน นั่นคือถอยกลับจากการทำให้ง่ายลงด้วยการเรียก `complicate()` ดังนั้นเมื่อเจอการปฏิเสธจากตัวกรองระหว่างการชริงก์ การชริงก์จะไม่สามารถดำเนินต่อไปยังค่าที่ง่ายกว่าค่าใดได้เลย แม้ว่าจะมีบางค่าที่ตัวกรองจะยอมรับก็ตาม
