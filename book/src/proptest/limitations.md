# ข้อจำกัดของการทดสอบพร็อพเพอร์ตี

หากเรามีเวลาไม่จำกัด การทดสอบพร็อพเพอร์ตีจะสามารถสุ่มตรวจครอบคลุมขอบเขตอินพุตทั้งหมด (input space) ของการทดสอบได้อย่างแน่นอน แต่ในความเป็นจริงเรามีเวลาจำกัด จึงทำได้เพียงสุ่มตรวจตัวอย่างบางส่วนจากขอบเขตอินพุตทั้งหมดเท่านั้น นั่นหมายความว่า การทดสอบพร็อพเพอร์ตีแทบจะไม่มีโอกาสค้นพบกรณีขอบเขต (edge cases) ที่เป็นค่าเดี่ยวๆ เจาะจงเพียงค่าเดียวในปริภูมิอินพุตขนาดมหึมา ตัวอย่างเช่น เทสต์ต่อไปนี้จะรันผ่านแทบทุกครั้ง:

```rust
# extern crate proptest;
use proptest::prelude::*;

proptest! {
    #[test]
    # fn dummy(0..1) {} // Doctests don't build `#[test]` functions, so we need this
    fn i64_abs_is_never_negative(a: i64) {
        // This actually fails if a == i64::MIN, but randomly picking one
        // specific value out of 2⁶⁴ is overwhelmingly unlikely.
        assert!(a.abs() >= 0);
    }
}
# fn main() { i64_abs_is_never_negative() }
```

ด้วยเหตุนี้ การเขียนยูนิตเทสต์แบบดั้งเดิมที่คัดเลือกเคสทดสอบและกรณีขอบเขตอย่างชาญฉลาดจึงยังคงเป็นสิ่งจำเป็นสำหรับปัญหาหลายประเภท

ในทำนองเดียวกัน ในบางสถานการณ์อาจเป็นเรื่องยากหรือแทบเป็นไปไม่ได้เลยที่จะนิยามกลยุทธ์ (strategy) ที่สามารถสร้างอินพุตที่มีประโยชน์จริง ตัวอย่างเช่น การใช้กลยุทธ์ `.{1,4096}` อาจเหมาะกับการยิงสุ่มทดสอบ (fuzz) ตัววิเคราะห์ไวยากรณ์ (parser) ของภาษา C แต่มันแทบจะไม่มีโอกาสสร้างโค้ดที่ถูกต้องตามหลักไวยากรณ์จนผ่านเข้าไปถึงขั้นตอนการสร้างโค้ด (code generator) ได้เลย
