# การทดสอบสเตตแมชชีน

เครต `proptest-state-machine` ให้การรองรับการทดสอบระบบด้วยแบบจำลองสเตตแมชชีน (State Machine Testing)

## ควรใช้การทดสอบสเตตแมชชีนเมื่อไหร่?

การทดสอบสเตตแมชชีนช่วยตรวจสอบพร็อพเพอร์ตีของระบบที่กำลังทดสอบ (System Under Test: SUT) เทียบกับแบบจำลองสเตตแมชชีนอ้างอิงเชิงนามธรรม (Abstract Reference State Machine) โดยอัตโนมัติ โดยระบบจะพยายามค้นหาตัวอย่างค้าน (counter-example) ที่ทำให้คุณสมบัติต่างๆ ของระบบไม่เป็นจริง แล้วทำการย่อขนาด (shrink) ลำดับขั้นตอนการเปลี่ยนสถานะ (transitions) ให้เหลือเป็นลำดับที่สั้นที่สุดที่ยังคงจำลองปัญหาเดิมได้

สเตตแมชชีนเป็นแบบจำลองเชิงนามธรรมที่มีประโยชน์อย่างยิ่งสำหรับการวิเคราะห์และทำความเข้าใจตรรกะของโค้ด ไม่ว่าจะเป็นตรรกะระดับล่าง (low-level) ไปจนถึงระดับสถาปัตยกรรม (high-level) ต่างก็สามารถจำลองให้อยู่ในรูปของสเตตแมชชีนได้ทั้งสิ้น โดยเฉพาะอย่างยิ่งกับโค้ดที่มีการเปลี่ยนแปลงสถานะภายใน (effectful code) ซึ่งการเขียนเทสต์ครอบคลุมด้วยตนเองทำได้ยาก หรือมีความซับซ้อนเกินกว่าจะพิสูจน์ความถูกต้องได้อย่างเป็นทางการ

ตัวอย่างระบบที่เหมาะสมต่อการนำมาทดสอบ ได้แก่:

- โครงสร้างข้อมูลที่มี API ซึ่งเปลี่ยนแปลงสถานะภายในของตนเอง
- เลเยอร์การเชื่อมต่อหรือจัดการฐานข้อมูล (Database APIs)
- การสื่อสารและโต้ตอบระหว่างไคลเอนต์กับเซิร์ฟเวอร์ (Client-server interactions)

คุณอาจต้องลงทุนลงแรงในช่วงแรกเพื่อตั้งค่าชุดการทดสอบ และโดยทั่วไปจะใช้เวลารันนานกว่าเทสต์พร็อพเพอร์ตีธรรมดาเล็กน้อย แต่หากความถูกต้องสมบูรณ์เป็นหัวใจสำคัญสำหรับระบบของคุณ ผลตอบแทนที่ได้คือชุดการทดสอบที่ตรวจจับบั๊กได้อย่างทรงพลังราวกับเวทมนตร์ และดังที่คุณจะได้เห็นต่อไป [คุณก็สามารถนำไปใช้เองได้ไม่ยาก](#กลไกการทำงาน) นอกจากนี้ เมื่อตั้งค่าโครงสร้างหลักเสร็จแล้ว การขยายผลและเพิ่มการตรวจสอบพร็อพเพอร์ตีใหม่ๆ ก็ทำได้อย่างสะดวกยิ่งขึ้น

## วิธีใช้งาน

ก่อนเริ่มต้นใช้งานการทดสอบสเตตแมชชีน ขอแนะนำให้คุณทำความคุ้นเคยกับแนวคิดพื้นฐานของ Proptest เสียก่อน เพราะระบบนี้ต่อยอดขึ้นมาจากกลไกหลักของ Proptest โดยตรง:

- กลยุทธ์ (Strategies) ต่างๆ ถูกสร้างขึ้นจากแกนหลักของ Proptest เพื่อใช้สร้างอินพุตสำหรับทดสอบสเตตแมชชีน
- เนื่องจากลำดับการเปลี่ยนสถานะ (transition sequence) ที่สร้างขึ้นมานั้นถือเป็นกลยุทธ์ในตัวเอง ระบบจึงสามารถย่อขนาด (shrink) ลำดับดังกล่าวได้เมื่อพบกรณีที่พร็อพเพอร์ตีไม่เป็นจริง
- ระบบจะบันทึกไฟล์ regression ที่บรรจุซีดเดิมไว้ ทำให้สามารถรันซ้ำเพื่อจำลองเคสเดิมได้อย่างแม่นยำ (deterministic replay)

สรุปสั้นๆ คือ คุณจะอิมพลีเมนต์เทรต `ReferenceStateMachine` และ `StateMachineTest` จากนั้นเรียกใช้มาโคร `prop_state_machine!` เพื่อสั่งรันการทดสอบ

หากต้องการเริ่มต้นอย่างรวดเร็ว ลองดูโค้ดตัวอย่างในโปรเจกต์:

- `state_machine_heap.rs` — โมเดลพื้นฐานสำหรับทดสอบ API ของโครงสร้างข้อมูลฮีป (heap)
- `state_machine_echo_server.rs` — โมเดลที่ซับซ้อนขึ้นสำหรับ echo server ที่มีหลายไคลเอนต์เชื่อมต่อพร้อมกัน

หากต้องการดูรายละเอียดขั้นตอนการเปลี่ยนสถานะ (transitions) ใน standard output ระหว่างที่เทสต์กำลังทำงาน สามารถรันโดยกำหนดค่า verbose เช่น: `PROPTEST_VERBOSE=1 cargo run --example state_machine_heap`

การทดสอบสเตตแมชชีนประกอบด้วย 2 ส่วนหลัก ได้แก่:
1. นิยามแบบจำลองสเตตแมชชีนอ้างอิงเชิงนามธรรม ซึ่งทำหน้าที่สร้างลำดับอินพุตและคำสั่งสำหรับการทดสอบ
2. นิยามการทดสอบสำหรับระบบจริง (SUT) ซึ่งจะนำลำดับการเปลี่ยนสถานะเดียวกันไปรันกับระบบจริง เพื่อเปรียบเทียบผลลัพธ์ ตรวจสอบหาข้อแตกต่าง หรือเงื่อนไขที่ทำให้พร็อพเพอร์ตี (เงื่อนไขหลังการทำงาน และอินแวเรียนต์) ไม่เป็นจริง

### กลยุทธ์ของสเตตแมชชีนอ้างอิง

คุณเริ่มต้นการทดสอบสเตตแมชชีนได้ด้วยการอิมพลีเมนต์เทรต `ReferenceStateMachine` ซึ่งใช้สำหรับสร้างลำดับการเปลี่ยนสถานะ และใช้เปรียบเทียบกับสถานะของระบบจริง (SUT) โดยเทรตนี้ต้องการชนิดข้อมูลร่วม (associated types) อย่างน้อย 2 ตัว:

- `type State` — แทนสถานะของสเตตแมชชีนอ้างอิง
- `type Transition` — บรรจุการเปลี่ยนสถานะที่เป็นไปได้ทั้งหมดของสเตตแมชชีน ซึ่งโดยปกติจะเป็น `enum` ที่แต่ละวาเรียนต์เก็บพารามิเตอร์อินพุตของขั้นตอนนั้นๆ (ถ้ามี)

นอกจากนี้คุณต้องอิมพลีเมนต์ฟังก์ชันหลัก 3 ฟังก์ชัน:

- ฟังก์ชันสำหรับสร้างสถานะเริ่มต้นของสเตตแมชชีนอ้างอิง:

  ```rust,ignore
  fn init_state() -> BoxedStrategy<Self::State>
  ```
  
  คุณสามารถสร้างสถานะแบบสุ่มผ่านกลยุทธ์ หรือใช้ `Just` เพื่อกำหนดค่าคงที่ก็ได้ ทั้งนี้ คุณสามารถแปลง `Strategy` ใดๆ ให้เป็น `BoxedStrategy` ได้ง่ายๆ ด้วยการเรียกใช้ `.boxed()`

- ฟังก์ชันสำหรับสร้างขั้นตอนการเปลี่ยนสถานะ:
  
  ```rust,ignore
  fn transitions(state: &Self::State) -> BoxedStrategy<Self::Transition>
  ```
  
  โดยทั่วไปมักใช้มาโคร `prop_oneof!` ที่จุดนี้ หากการเปลี่ยนสถานะต้องการพารามิเตอร์อินพุต คุณสามารถสุ่มสร้างค่านั้นด้วย `Strategy` แล้วเรียก `.prop_map` เพื่อห่อเข้าไปในวาเรียนต์ของ `Transition` สำหรับสเตตแมชชีนที่ซับซ้อน ชุดการเปลี่ยนสถานะที่ถูกต้องอาจขึ้นอยู่กับสถานะปัจจุบัน คุณจึงสามารถอ่านข้อมูลจากอาร์กิวเมนต์ `state` ได้ ซึ่งอาจนำไปใช้ร่วมกับฟังก์ชัน `proptest::sample::select` เพื่อสุ่มเลือกค่าจากอาร์เรย์หรือคอลเลกชัน (ข้อควรระวัง: ห้ามเรียก `select` กับอาร์เรย์ว่าง เพราะจะทำให้เกิดข้อผิดพลาดที่ระบุสาเหตุได้ยาก) ตัวอย่างเช่น หากต้องการลบคีย์ออกจาก hash map คุณสามารถสุ่มเลือกคีย์ที่มีอยู่จริงจากสถานะปัจจุบันแล้วแปลงเป็นคำสั่ง transition ทั้งนี้ เมื่อใช้วิธีนี้ คุณจำเป็นต้องโอเวอร์ไรด์ `fn preconditions` ด้วย ซึ่งจะอธิบายเพิ่มเติมด้านล่าง

- ฟังก์ชันสำหรับนำการเปลี่ยนสถานะไปคำนวณกับสถานะอ้างอิง:

  ```rust,ignore
  fn apply(mut state: Self::State, transition: &Self::Transition) -> Self::State
  ```

นอกจากนี้ คุณยังสามารถโอเวอร์ไรด์ฟังก์ชันเริ่มต้นของ:

```rust,ignore
fn preconditions(state: &Self::State, transition: &Self::Transition) -> bool
```

โดยค่าเริ่มต้น ฟังก์ชันนี้จะคืนค่า `true` เสมอ ซึ่งหมายความว่าไม่มีเงื่อนไขบังคับก่อนทำงาน แต่เงื่อนไขก่อนทำงาน (pre-conditions) เป็นวิธีจำกัดว่าการเปลี่ยนสถานะใดบ้างที่ถูกต้องตามกฎของสถานะปัจจุบัน ซึ่งคุณควรกำหนดเฉพาะเงื่อนไขที่ขึ้นอยู่กับสถานะปัจจุบันเท่านั้น เพื่อให้มั่นใจได้ว่าสเตตแมชชีนอ้างอิงจะสร้างและย่อขนาด (shrink) เฉพาะลำดับคำสั่งที่ถูกต้องตามตรรกะเท่านั้น จุดที่มักมองข้ามคือ สถานะปัจจุบันอาจได้รับผลกระทบจากกระบวนการชริงก์ เช่น ในตัวอย่างการสุ่มคีย์จาก hash map ใน `fn transitions` คุณจำเป็นต้องตรวจสอบใน preconditions ว่าคีย์นั้นยังคงหลงเหลืออยู่ใน hash map จริงหรือไม่ เพราะหลังจากผ่านการชริงก์ คีย์ดังกล่าวอาจถูกตัดทอนออกไปก่อนแล้ว

คุณสามารถอิมพลีเมนต์เทรต `ReferenceStateMachine` ได้ 2 รูปแบบ:

- บนโครงสร้างข้อมูลที่จะใช้แทนสเตตแมชชีนอ้างอิงโดยตรง แล้วกำหนด `type State = Self;` หรือ
- บน `struct` เปล่า (unit struct) ซึ่งจะสะดวกกว่าหากคุณนำชนิดข้อมูลภายนอกมาใช้เป็น `type State`

### การนิยามเทสต์สเตตแมชชีน

เมื่อเตรียมส่วนอ้างอิงเรียบร้อยแล้ว คุณสามารถอิมพลีเมนต์เทรต `StateMachineTest` ต่อได้เลย ซึ่งต้องการชนิดข้อมูลร่วม 2 ตัวเช่นกัน:

- `type SystemUnderTest` — ชนิดข้อมูลที่แทนระบบจริงที่กำลังทดสอบ (SUT)
- `type Reference` — ชนิดข้อมูลที่คุณได้อิมพลีเมนต์เทรต `ReferenceStateMachine` ไว้ก่อนหน้านี้

และมีฟังก์ชันร่วม 3 ฟังก์ชันที่ต้องนำไปเขียนอิมพลีเมนต์ (ปรับชนิดข้อมูลให้เข้าใจง่ายขึ้นเพื่อความชัดเจน):

- เริ่มต้นสถานะของระบบจริง (SUT):

  ```rust,ignore
  fn init_test(ref_state: &Self::Reference::State) -> Self::SystemUnderTest
  ```
  
  หาก `ReferenceStateMachine::init_state` ของคุณใช้กลยุทธ์ที่สร้างค่าแบบสุ่ม คุณต้องนำ `ref_state` มาใช้ตั้งค่าเริ่มต้นให้กับ SUT ด้วย เพื่อให้แน่ใจว่าสถานะเริ่มต้นของทั้งสองฝั่งตรงกัน

- นำคำสั่ง `transition` ไปรันกับระบบจริง (SUT):
  
  ```rust,ignore
  fn apply(
    mut state: Self::SystemUnderTest,
    ref_state: &Self::Reference::State,
    transition: Transition
  ) -> Self::SystemUnderTest
  ```
  
  จุดนี้คือตำแหน่งที่คุณจะตรวจสอบเงื่อนไขหลังการทำงาน (post-conditions) ที่เกี่ยวข้องกับการเปลี่ยนสถานะนั้นๆ ดังนั้นหลังจากสั่งให้ระบบจริงทำงานตามคำสั่งแล้ว คุณสามารถใช้ `assert!` ตรวจสอบคุณสมบัติต่างๆ หรือนำ `ref_state` มาเปรียบเทียบผลลัพธ์เพิ่มเติมได้ โดย `ref_state` ในจุดนี้จะเป็นสถานะที่ผ่านการรันคำสั่ง transition เดียวกันนี้มาเรียบร้อยแล้ว

- ตรวจสอบคุณสมบัติที่ไม่แปรเปลี่ยน (Invariants) ในทุกสถานะ:

  ```rust,ignore
  fn check_invariants(state: &Self::SystemUnderTest, ref_state: &Self::Reference::State)
  ```

  คุณสมบัติเหล่านี้ต้องเป็นจริงอยู่เสมอทุกครั้ง และจะถูกตรวจสอบหลังจบทุกทรานซิชัน เช่นเดียวกับใน `apply` คุณสามารถนำ `ref_state` มาช่วยเปรียบเทียบได้ตามต้องการ

หากต้องการเพิ่มตรรกะการเคลียร์ทรัพยากร (cleanup) เมื่อสิ้นสุดแต่ละกรณีทดสอบ คุณสามารถโอเวอร์ไรด์ฟังก์ชัน `teardown` ได้ ซึ่งค่าเริ่มต้นจะเพียงแค่ drop สถานะทิ้ง:

```rust,ignore
fn teardown(state: Self::SystemUnderTest, ref_state: Self::Reference::State)
```

### ทำให้เทสต์สเตตแมชชีนรันได้

ขั้นตอนสุดท้าย เมื่อต้องการสั่งรัน `StateMachineTest` คุณสามารถเรียกใช้มาโคร `prop_state_machine!` ได้ดังตัวอย่าง:

```rust,ignore
prop_state_machine! {
  #[test]
  fn name_of_the_test(sequential 1..20 => MyStateMachineTest);
}
```

โดยคุณตั้งชื่อฟังก์ชัน `name_of_the_test` และระบุตัวเลขค่าเดี่ยวหรือช่วงตัวเลขหลังคีย์เวิร์ด `sequential` เพื่อกำหนดจำนวนทรานซิชันที่จะสุ่มสร้างขึ้นในการรันแต่ละรอบ ส่วน `MyStateMachineTest` คือ struct ที่คุณอิมพลีเมนต์เทรต `StateMachineTest` ไว้

เพียงเท่านี้การตั้งค่าก็เสร็จสมบูรณ์ คุณสามารถสั่งรันเทสต์ และอาจใช้เครื่องมืออย่าง `cargo watch` เพื่อช่วยทดสอบระหว่างการพัฒนา แล้วรอดูว่า Proptest จะค้นพบตัวอย่างค้าน (counter-example) ที่น่าสนใจในระบบของคุณหรือไม่

### เคล็ดลับเพิ่มเติม

เนื่องจากการทดสอบสเตตแมชชีนใช้ทรัพยากรมากกว่าการทดสอบพร็อพเพอร์ตีทั่วไป หากคุณรันเทสต์บนระบบ CI คุณอาจต้องการปรับค่า `cases` ใน `proptest_config` เพื่อลดหรือเพิ่มจำนวนรอบการทดสอบ หรือจะตั้งค่าผ่านตัวแปรสภาพแวดล้อม `PROPTEST_CASES` ก็ได้เช่นกัน และในระหว่างการพัฒนา คุณสามารถปรับค่านี้ให้รันจำนวนเคสมากๆ เพื่อเพิ่มโอกาสในการดักจับข้อบกพร่องที่ซ่อนอยู่

> เมื่อคาดกันว่ายังมีสิ่งมีชีวิตอีกประมาณสี่ล้านสปีชีส์ที่เรายังไม่ได้ตั้งชื่อให้ด้วยซ้ำ ไม่ต้องสงสัยเลยว่านักวิทยาศาสตร์จะยังคงเพลิดเพลินและยุ่งอยู่กับการศึกษาสิ่งมีชีวิตเหล่านี้ต่อไปอีกหลายพันปี ตราบใดที่ยังมีแมลงให้ศึกษาอยู่ โลกนี้จะไม่ยากจน น่าประหลาดใจ และน่าอัศจรรย์น้อยลงไปหรือ หากสิ่งมีชีวิตแปลกประหลาดเหล่านี้ไม่มีอยู่จริง
>
> -- <cite>Dave Goulson, Silent Earth</cite>

เอาละ เรามาปล่อยเจ้าแมลง (bugs) ไว้ในธรรมชาติ แล้วไปมุ่งมั่นกำจัดข้อบกพร่อง (defects) ในโค้ดกันดีกว่า!

เนื่องจากผลลัพธ์ของกรณีทดสอบที่ล้มเหลวอาจมีข้อมูลมากจนอ่านยาก การสั่งให้แสดงรายละเอียดของทรานซิชันระหว่างทางจึงมีประโยชน์อย่างยิ่ง คุณสามารถทำได้โดยกำหนดค่า `verbose` ใน `proptest_config` เป็น `1` หรือสูงกว่า และเช่นเดียวกัน หากคุณไม่ต้องการแก้โค้ดคอนฟิก ก็สามารถใช้ตัวแปรสภาพแวดล้อม `PROPTEST_VERBOSE` แทนได้

อีกหนึ่งตัวเลือกคอนฟิกที่มีประโยชน์คือ `timeout` (หรือกำหนดผ่าน `PROPTEST_TIMEOUT`) สำหรับการทดสอบที่ต้องใช้เวลาประมวลผลนานขึ้น

## กลไกการทำงาน

หัวข้อนี้จะอธิบายเจาะลึกถึงกลไกการทำงานภายในของระบบสเตตแมชชีน (โดยละเว้นรายละเอียดปลีกย่อยบางส่วน) หากคุณต้องการเพียงแค่ใช้งานทั่วไป สามารถข้ามหัวข้อนี้ไปได้

ฟังก์ชัน `ReferenceStateMachine::sequential_strategy` จะทำหน้าที่สร้างกลยุทธ์ `Sequential` ขึ้นมา ซึ่งจะผลิตลำดับของทรานซิชันตามที่นิยามไว้ใน `ReferenceStateMachine` ความถูกต้องของแต่ละทรานซิชันในลำดับจะถูกตรวจสอบเทียบกับสถานะปัจจุบันของสเตตแมชชีนผ่าน `ReferenceStateMachine::preconditions` (ถ้ามี) จากนั้นสถานะจะถูกอัปเดตตามคำสั่งทรานซิชันนั้นด้วยฟังก์ชัน `ReferenceStateMachine::apply`

หลังจากนั้น กลยุทธ์ `Sequential` จะถูกส่งต่อไปยังตัวประมวลผลของ Proptest เช่นเดียวกับกลยุทธ์ทั่วไป ผ่านมาโคร `prop_state_machine!` ซึ่งจะสร้าง `Vec<Transition>` ส่งต่อไปให้ `StateMachineTest::test_sequential` นำไปรันกับระบบจริง (SUT) ทีละขั้นตอน พร้อมทั้งตรวจสอบเงื่อนไขหลังและอินแวเรียนต์ตลอดกระบวนการ หากพบกรณีที่การทดสอบล้มเหลว กระบวนการชริงก์ (shrinking) ก็จะเริ่มทำงานทันทีเพื่อย่อขนาดเคสให้เล็กที่สุด

กลยุทธ์การชริงก์ถูกกำหนดโดย `type Tree = SequentialValueTree` ซึ่งเป็น associated type ของกลยุทธ์ `Sequential` โดยจะนำขั้นตอน `Shrink::InitialState`, `Shrink::DeleteTransition` และ `Shrink::Transition` มาวนซ้ำอย่างเป็นระบบ (ดูโค้ดจริงได้ที่ `proptest/src/strategy/state_machine.rs`):

1. ระบบจะเริ่มต้นด้วยการพยายามลบทรานซิชันออกจากท้ายรายการไปเรื่อยๆ จนกว่าจะลบต่อไม่ได้ (จนถึงค่า `min_size` ซึ่งกำหนดจากช่วงจำนวนทรานซิชันตอนเรียก `prop_state_machine!`)
2. จากนั้น ระบบจะพยายามย่อขนาด (shrink) แต่ละทรานซิชันที่เหลืออยู่ โดยคราวนี้จะเริ่มจากหัวแถวไปยังท้ายแถวตามลำดับการทำงานจริง
3. ขั้นสุดท้าย ระบบจะพยายามย่อขนาดสถานะเริ่มต้น (initial state) จนกว่าจะย่อเล็กลงไปกว่านั้นไม่ได้อีก

ประวัติการชริงก์ขั้นล่าสุดจะถูกบันทึกไว้ใน `SequentialValueTree` เสมอ ดังนั้นหากการย่อขนาดไปจบลงที่เคสซึ่งไม่ทำให้เกิดข้อผิดพลาดเดิมอีกต่อไป การเรียกเมธอด `complicate` บน `ValueTree` ของ `SequentialValueTree` จะช่วยถอยกลับ (backtrack) ไปยังเคสที่ยังคงแสดงปัญหาได้

## เทคโนโลยีที่คล้ายกัน

การทดสอบสเตตแมชชีนของ Proptest ได้รับแรงบันดาลใจอย่างมากจาก eqc_statem ของ Erlang (อ่านเพิ่มเติมได้ที่ [Finding Race Conditions in Erlang with QuickCheck and PULSE](https://smallbone.se/papers/finding-race-conditions.pdf)) โดยมีความแตกต่างที่สำคัญบางประการ ได้แก่:

- ปัจจุบันรองรับเฉพาะกลยุทธ์แบบเรียงลำดับ (sequential) แต่มีแผนจะเพิ่มกลยุทธ์แบบทำงานพร้อมกัน (concurrent) ในอนาคต
- ไม่มีการใช้ตัวแปรเชิงสัญลักษณ์ ("symbolic" variables) แบบใน eqc_statem โดยสถานะของแบบจำลองอ้างอิงเชิงนามธรรมจะถูกแยกขาดจากสถานะของระบบจริงที่กำลังทดสอบ
- เงื่อนไขหลังการทำงานไม่ได้แยกเป็นฟังก์ชันต่างหาก แต่ถูกรวมไว้เป็นส่วนหนึ่งของฟังก์ชัน `StateMachineTest::apply`
