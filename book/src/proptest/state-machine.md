# การทดสอบสเตตแมชชีน

การรองรับการทดสอบสเตตแมชชีนมีอยู่ในครีต `proptest-state-machine`

## ควรใช้การทดสอบสเตตแมชชีนเมื่อไหร่?

การทดสอบสเตตแมชชีนช่วยตรวจสอบพร็อพเพอร์ตีของระบบที่ทดสอบ (SUT) เทียบกับนิยามสเตตแมชชีนอ้างอิงเชิงนามธรรมโดยอัตโนมัติ โดยพยายามค้นหาตัวอย่างค้านที่ทำให้พร็อพเพอร์ตีที่นิยามไว้ของระบบเป็นเท็จ แล้วพยายามชริงก์มันลงเป็นลำดับทรานซิชันที่เล็กที่สุดที่ยังคงทำให้เกิดปัญหาเดิมอยู่

สเตตแมชชีนเป็นนามธรรมที่มีประโยชน์มากสำหรับการให้เหตุผลเกี่ยวกับโค้ด หลายสิ่งตั้งแต่ตรรกะระดับต่ำไปจนถึงระดับสูง และอยู่ตรงไหนก็ตามในระหว่างนั้น ล้วนจำลองเป็นสเตตแมชชีนได้ทั้งสิ้น สเตตแมชชีนมีประสิทธิผลมากสำหรับการจำลองโค้ดที่มีผลข้างเคียง (effectful code) นั่นคือโค้ดที่เปลี่ยนแปลงสถานะบางอย่าง ซึ่งอาจยากเกินกว่าจะทดสอบให้ครอบคลุมด้วยวิธีการแบบใช้แรงคน หรือซับซ้อนเกินกว่าจะพิสูจน์อย่างเป็นทางการได้

ตัวอย่างที่เหมาะสมพอจะช่วยให้เห็นภาพได้แก่ (ไม่ใช่รายการทั้งหมด):

- โครงสร้างข้อมูลที่มี API ซึ่งเปลี่ยนสถานะของตัวเอง
- API สำหรับฐานข้อมูล
- การโต้ตอบระหว่างไคลเอนต์กับเซิร์ฟเวอร์

คุณต้องลงทุนช่วงแรกบ้างในการตั้งค่าเทสต์ และโดยทั่วไปแล้วมันใช้เวลารันนานกว่าเทสต์พร็อพเพอร์ตีธรรมดาเล็กน้อย แต่ถ้าความถูกต้องเป็นสิ่งสำคัญสำหรับกรณีการใช้งานของคุณ คุณจะได้ผลตอบแทนเป็นเทสต์ที่มีประสิทธิภาพในการค้นหาบั๊กจนรู้สึกเหมือนเวทมนตร์ แต่ดังที่คุณจะได้เห็น [คุณก็สามารถนำไปใช้เองได้ไม่ยาก](#how-does-it-work) นอกจากนี้ เมื่อตั้งค่าเทสต์เสร็จแล้ว การขยายและเพิ่มพร็อพเพอร์ตีใหม่ๆ ให้ตรวจสอบก็ทำได้ง่ายกว่ามาก

## วิธีใช้งาน

ก่อนใช้การทดสอบสเตตแมชชีน แนะนำให้คุณคุ้นเคยกับแนวคิดพื้นฐานของ Proptest เองเสียก่อนเป็นอย่างน้อย เนื่องจากมันถูกสร้างขึ้นบนรากฐานสำคัญของ Proptest นั่นคือ:

- กลยุทธ์ต่างๆ ประกอบขึ้นจากโครงสร้างพื้นฐานของ proptest และใช้สร้างอินพุตให้กับการทดสอบสเตตแมชชีน
- เนื่องจากลำดับทรานซิชันที่สร้างขึ้นนั้นเป็นกลยุทธ์ในตัวเอง เทสต์จะพยายามชริงก์มันเมื่อพบเคสที่ทำให้พร็อพเพอร์ตีบางอย่างเป็นเท็จ
- มันจะบันทึกไฟล์รีเกรสชันที่บรรจุซีดซึ่งใช้ทำซ้ำเคสที่พบได้อย่างดีเทอร์มินิสติก

พูดสั้นๆ คือ ใช้ `ReferenceStateMachine` และ `StateMachineTest` ในการนำการทดสอบสเตตแมชชีนไปใช้ แล้วใช้มาโคร `prop_state_machine!` เพื่อรันมัน

ถ้าคุณแค่อยากเริ่มต้นอย่างรวดเร็ว ลองดูตัวอย่างเหล่านี้:

- `state_machine_heap.rs` - โมเดลง่ายๆ สำหรับทดสอบ API ของโครงสร้างข้อมูลฮีป
- `state_machine_echo_server.rs` - โมเดลที่ซับซ้อนกว่าสำหรับ echo server ที่มีไคลเอนต์หลายรายเชื่อมต่อ

หากต้องการเห็นว่าทรานซิชันใดถูกนำไปใช้ในเอาต์พุตมาตรฐานระหว่างที่เทสต์สเตตแมชชีนทำงาน ให้รันคำสั่งเหล่านี้เช่น `PROPTEST_VERBOSE=1 cargo run --example state_machine_heap`

การทดสอบสเตตแมชชีนประกอบด้วยสองส่วน ได้แก่ นิยามสเตตแมชชีนอ้างอิงเชิงนามธรรมที่ขับเคลื่อนอินพุตให้กับการทดสอบ และนิยามเทสต์สำหรับ SUT ที่ทำทรานซิชันเดียวกันกับสเตตแมชชีนอ้างอิงซ้ำ เพื่อค้นหาความแตกต่างที่เป็นไปได้หรือเงื่อนไขที่ทำให้พร็อพเพอร์ตีที่นิยามไว้ (ในที่นี้คือเงื่อนไขหลังและอินแวเรียนต์) เริ่มเป็นเท็จ

### กลยุทธ์ของสเตตแมชชีนอ้างอิง

คุณเริ่มต้นการทดสอบสเตตแมชชีนได้ด้วยการนำเทรต `ReferenceStateMachine` ไปใช้ ซึ่งใช้ขับเคลื่อนการสร้างลำดับทรานซิชัน และยังใช้เปรียบเทียบกับสถานะของ SUT ได้ด้วย อย่างน้อยเทรตนี้ต้องการชนิดข้อมูลร่วมสองชนิด:

- `type State` ซึ่งแทนสถานะของสเตตแมชชีนอ้างอิง
- `type Transition` ซึ่งบรรจุทรานซิชันที่เป็นไปได้ของสเตตแมชชีน ปกติแล้วจะเป็น `enum` ที่วาเรียนต์ของมันบรรจุพารามิเตอร์อินพุตของทรานซิชัน (ถ้ามี)

คุณยังต้องนำฟังก์ชันร่วมสามฟังก์ชันไปใช้ด้วย:

- ฟังก์ชันสำหรับเริ่มต้นสเตตแมชชีนอ้างอิง:

  ```rust,ignore
  fn init_state() -> BoxedStrategy<Self::State>
  ```
  
  คุณสามารถสร้างสถานะแบบสุ่มด้วยกลยุทธ์ หรือใช้กลยุทธ์ `Just` สำหรับค่าคงที่ก็ได้ โปรดทราบว่าคุณสามารถสร้าง `BoxedStrategy` จาก `Strategy` ใดก็ได้ เพียงเรียก `.boxed()` กับมัน

- ฟังก์ชันสำหรับสร้างทรานซิชัน:
  
  ```rust,ignore
  fn transitions(state: &Self::State) -> BoxedStrategy<Self::Transition>
  ```
  
  ส่วนใหญ่แล้วคุณจะใช้ `prop_oneof!` ตรงนี้ หากทรานซิชันรับพารามิเตอร์อินพุต คุณสามารถสร้างมันด้วย `Strategy` แล้ว `.prop_map` ไปยังวาเรียนต์ของ `Transition` ได้ ในสเตตแมชชีนที่ซับซ้อนกว่า ชุดทรานซิชันที่ถูกต้องอาจขึ้นอยู่กับสถานะปัจจุบัน ด้วยเหตุนี้ คุณจึงสามารถใช้อาร์กิวเมนต์ `state` ซึ่งอาจใช้ร่วมกับฟังก์ชัน `proptest::sample::select` ที่ช่วยให้คุณสร้างกลยุทธ์ซึ่งเลือกค่าสุ่มจากอาเรย์หรือคอลเลกชันที่คล้ายอาเรย์ได้ (ระวังอย่าเรียก `select` กับอาเรย์ว่าง เพราะจะทำให้ล้มเหลวในลักษณะที่ค่อนข้างคลุมเครือ) ตัวอย่างเช่น หากคุณต้องการลบคีย์ตัวใดตัวหนึ่งที่มีอยู่จาก hash map คุณสามารถเลือกคีย์ตัวหนึ่งจากสถานะปัจจุบันแล้วแมปมันเป็นทรานซิชัน โปรดทราบว่าเมื่อทำแบบนี้ คุณจะต้องโอเวอร์ไรด์ `fn preconditions` ด้วย ซึ่งอธิบายรายละเอียดเพิ่มเติมไว้ด้านล่าง

- ฟังก์ชันสำหรับนำทรานซิชันที่กำหนดไปใช้กับสถานะอ้างอิง:

  ```rust,ignore
  fn apply(mut state: Self::State, transition: &Self::Transition) -> Self::State
  ```

นอกจากนี้ คุณอาจต้องการโอเวอร์ไรด์การนำไปใช้เริ่มต้นของ:

```rust,ignore
fn preconditions(state: &Self::State, transition: &Self::Transition) -> bool
```

โดยค่าเริ่มต้น ฟังก์ชันนี้เพียงคืนค่า `true` ซึ่งหมายความว่าไม่มีเงื่อนไขก่อน เงื่อนไขก่อนเป็นวิธีจำกัดว่าทรานซิชันใดบ้างที่ถูกต้องสำหรับสถานะหนึ่งๆ และคุณจะต้องจำกัดเฉพาะทรานซิชันที่ความถูกต้องขึ้นอยู่กับสถานะปัจจุบันเท่านั้น วิธีนี้ทำให้มั่นใจได้ว่าสเตตแมชชีนอ้างอิงจะสร้างและชริงก์ได้เฉพาะลำดับทรานซิชันที่ถูกต้องเท่านั้น อาจไม่เห็นได้ชัดในทันทีว่าสถานะปัจจุบันอาจได้รับผลกระทบจากการชริงก์ จากตัวอย่างการเลือกคีย์ของ hash map สำหรับ `fn transitions` คุณจะต้องตรวจสอบว่าคีย์ของทรานซิชันยังอยู่ใน hash map อยู่ ซึ่งอาจไม่เป็นจริงอีกต่อไปหลังจากมีการชริงก์ไปแล้ว

คุณจะนำเทรต `ReferenceStateMachine` ไปใช้กับสิ่งใดสิ่งหนึ่งต่อไปนี้ก็ได้:

- โครงสร้างข้อมูลที่จะแทนสเตตแมชชีนอ้างอิงของคุณ และกำหนด `type State = Self;` หรือ
- `struct` ว่างเปล่า ซึ่งอาจสะดวกกว่าการสร้างชนิดข้อมูลตัวห่อ หากคุณใช้ชนิดข้อมูลจากภายนอกเป็น `type State`

### การนิยามเทสต์สเตตแมชชีน

เมื่อจัดการตรงนั้นเรียบร้อยแล้ว คุณก็สามารถนำเทรต `StateMachineTest` ไปใช้ได้เลย ซึ่งก็ต้องการชนิดข้อมูลร่วมสองชนิดเช่นกัน:

- `type SystemUnderTest` ซึ่งเป็นชนิดข้อมูลที่แทน SUT
- `type Reference` ซึ่งเป็นชนิดข้อมูลที่คุณนำเทรต `ReferenceStateMachine` ไปใช้ด้วย

นอกจากนี้ยังมีฟังก์ชันร่วมสามฟังก์ชันที่ต้องนำไปใช้ (บางชนิดข้อมูลถูกทำให้ง่ายลงเล็กน้อยเพื่อความชัดเจน):

- เริ่มต้นสถานะของ SUT:

  ```rust,ignore
  fn init_test(ref_state: &Self::Reference::State) -> Self::SystemUnderTest
  ```
  
  หาก `ReferenceStateMachine::init_state` ของคุณใช้กลยุทธ์ที่ไม่ใช่ค่าคงที่ คุณต้องใช้ `ref_state` ในการเริ่มต้นค่านี้ให้เป็นสถานะที่สอดคล้องกัน เพื่อให้แน่ใจว่าสถานะเริ่มต้นทั้งสองฝั่งสอดคล้องกัน

- นำ `transition` ไปใช้กับสถานะของ SUT:
  
  ```rust,ignore
  fn apply(
    mut state: Self::SystemUnderTest,
    ref_state: &Self::Reference::State,
    transition: Transition
  ) -> Self::SystemUnderTest
  ```
  
  ตรงนี้ก็เป็นที่ที่คุณจะตรวจสอบเงื่อนไขหลังใดๆ ที่ใช้กับทรานซิชันที่กำหนด ดังนั้นหลังจากนำทรานซิชันไปใช้กับสถานะแล้ว คุณสามารถ `assert!` พร็อพเพอร์ตีบางอย่างได้ หรืออาจใช้ `ref_state` ในการเปรียบเทียบเพิ่มเติมก็ได้ โดย `ref_state` นั้นจะถูกนำทรานซิชันเดียวกันกับที่ส่งให้ฟังก์ชันนี้ไปใช้แล้ว

- ตรวจสอบพร็อพเพอร์ตีที่ใช้ได้ในทุกสถานะ:

  ```rust,ignore
  fn check_invariants(state: &Self::SystemUnderTest, ref_state: &Self::Reference::State)
  ```

  พร็อพเพอร์ตีเหล่านี้ต้องเป็นจริงเสมอ และจะถูกตรวจสอบหลังทุกทรานซิชัน เช่นเดียวกับ `apply` คุณมีทางเลือกที่จะใช้ `ref_state` ในการเปรียบเทียบได้

หากต้องการเพิ่มตรรกะการเก็บกวาดให้รันตอนท้ายของแต่ละกรณีทดสอบ คุณสามารถโอเวอร์ไรด์ฟังก์ชัน `teardown` ได้ ซึ่งโดยค่าเริ่มต้นจะเพียง drop สถานะทิ้ง:

```rust,ignore
fn teardown(state: Self::SystemUnderTest, ref_state: Self::Reference::State)
```

### ทำให้เทสต์สเตตแมชชีนรันได้

สุดท้าย หากต้องการรัน `StateMachineTest` คุณสามารถใช้มาโคร `prop_state_machine!` ได้ ตัวอย่างเช่น:

```rust,ignore
prop_state_machine! {
  #[test]
  fn name_of_the_test(sequential 1..20 => MyStateMachineTest);
}
```

คุณตั้งชื่อ `name_of_the_test` และระบุตัวเลขค่าเดียวหรือช่วงตัวเลขหลังคีย์เวิร์ด `sequential` เพื่อกำหนดจำนวนทรานซิชันที่จะสร้างสำหรับการทำงานของสเตตแมชชีน ส่วน `MyStateMachineTest` คืออะไรก็ตามที่คุณนำเทรต `StateMachineTest` ไปใช้ด้วย

เท่านี้ก็เรียบร้อย คุณสามารถรันเทสต์ได้ อาจใช้ `cargo watch` ช่วยระหว่างพัฒนาต่อ และดูว่ามันจะพบตัวอย่างค้านที่น่าสนใจสำหรับพร็อพเพอร์ตีของคุณหรือไม่

### เคล็ดลับเพิ่มเติม

เนื่องจากการทดสอบสเตตแมชชีนอาจหนักกว่าเทสต์พร็อพเพอร์ตีทั่วไป หากคุณรันเทสต์ใน CI คุณอาจต้องการโอเวอร์ไรด์ค่า `cases` ของ `proptest_config` เริ่มต้น เพื่อให้รันเคสมากขึ้นหรือน้อยลงในการรันครั้งเดียว คุณยังใช้ตัวแปรสภาพแวดล้อม `PROPTEST_CASES` ได้ด้วย และระหว่างพัฒนาควรโอเวอร์ไรด์ค่านี้ให้รันหลายๆ เคส เพื่อเพิ่มโอกาสในการจับเจ้า~~บั๊ก~~ เอ่อ ข้อบกพร่องพวกนี้ให้ได้

> เมื่อคาดกันว่ายังมีสิ่งมีชีวิตอีกประมาณสี่ล้านสปีชีส์ที่เรายังไม่ได้ตั้งชื่อให้ด้วยซ้ำ ไม่ต้องสงสัยเลยว่านักวิทยาศาสตร์จะยังคงเพลิดเพลินและยุ่งอยู่กับการศึกษาสิ่งมีชีวิตเหล่านี้ต่อไปอีกหลายพันปี ตราบใดที่ยังมีแมลงให้ศึกษาอยู่ โลกนี้จะไม่ยากจน น่าประหลาดใจ และน่าอัศจรรย์น้อยลงไปหรือ หากสิ่งมีชีวิตแปลกประหลาดเหล่านี้ไม่มีอยู่จริง
>
> -- <cite>Dave Goulson, Silent Earth</cite>

เอาละ เรามาปล่อยเจ้า bugs ไว้ แล้วไปบดขยี้ defects กันแทนดีกว่า!

เนื่องจากเอาต์พุตของกรณีทดสอบที่ล้มเหลวอาจอ่านได้ยากสักหน่อย จึงมักสะดวกที่จะพิมพ์ทรานซิชันออกมา คุณทำได้โดยตั้งค่า `verbose` ของ `proptest_config` เป็น `1` หรือสูงกว่า และเช่นเดิม หากคุณไม่อยากเก็บค่านี้ไว้ในการตั้งค่าเทสต์ หรือต้องการโอเวอร์ไรด์การตั้งค่า คุณก็ใช้ตัวแปรสภาพแวดล้อม `PROPTEST_VERBOSE` แทนได้

ตัวเลือกการตั้งค่าที่มีประโยชน์อีกอย่างที่ควรรู้คือ `timeout` (หรือ `PROPTEST_TIMEOUT` ผ่านตัวแปรสภาพแวดล้อม) สำหรับเทสต์ที่อาจใช้เวลารันนานขึ้น

## กลไกการทำงาน

หัวข้อนี้จะลงลึกถึงกลไกภายในว่าสเตตแมชชีนถูกนำไปใช้อย่างไร โดยข้ามรายละเอียดที่ไม่น่าสนใจบางส่วนไป หากคุณสนใจเพียงการใช้งาน ก็ถือว่าหัวข้อนี้เป็นส่วนเสริมที่อ่านหรือไม่ก็ได้

`ReferenceStateMachine::sequential_strategy` จะตั้งค่ากลยุทธ์ `Sequential` ที่สร้างลำดับทรานซิชันจากนิยามของ `ReferenceStateMachine` ความยอมรับได้ของแต่ละทรานซิชันในลำดับนั้นขึ้นอยู่กับสถานะปัจจุบันของสเตตแมชชีนและ `ReferenceStateMachine::preconditions` (ถ้ามี) ส่วนสถานะจะถูกอัปเดตด้วยทรานซิชันผ่านฟังก์ชัน `ReferenceStateMachine::apply`

จากนั้นกลยุทธ์ `Sequential` จะถูกป้อนเข้าสู่ Proptest เหมือนกลยุทธ์อื่นๆ ผ่านมาโคร `prop_state_machine!` และมันจะสร้าง `Vec<Transition>` ที่ถูกส่งต่อไปยัง `StateMachineTest::test_sequential` ซึ่งจะนำไปใช้กับ SUT ทีละตัว เงื่อนไขหลังและอินแวเรียนต์จะถูกตรวจสอบระหว่างกระบวนการนี้ และหากพบเคสที่ล้มเหลว กระบวนการชริงก์ก็จะเริ่มทำงานไปจนกว่าจะชริงก์ต่อไม่ได้อีก

กลยุทธ์การชริงก์ซึ่งนิยามโดย `type Tree = SequentialValueTree` ที่เป็นชนิดข้อมูลร่วมของกลยุทธ์ `Sequential` คือการนำ `Shrink::InitialState`, `Shrink::DeleteTransition` และ `Shrink::Transition` ไปใช้แบบวนซ้ำ (ดูได้ใน `proptest/src/strategy/state_machine.rs`):

1. เราเริ่มต้นด้วยการพยายามลบทรานซิชันจากท้ายรายการ ไปเรื่อยๆ จนกว่าจะลบไม่ได้อีก (รายการถึง `min_size` แล้ว นั่นคือตัวแปรที่กำหนดจากช่วงจำนวนทรานซิชันที่เลือกไว้ตอนเรียกใช้ `prop_state_machine!`)
2. จากนั้น เราพยายามชริงก์ทรานซิชันแต่ละตัวอย่างวนซ้ำอีกครั้ง แต่คราวนี้เริ่มจากต้นรายการ ตั้งแต่ทรานซิชันแรกที่จะถูกนำไปใช้
3. สุดท้าย เราพยายามชริงก์สถานะเริ่มต้นจนกว่าจะชริงก์ต่อไม่ได้อีก

การชริงก์ครั้งสุดท้ายที่นำไปใช้จะถูกเก็บไว้ใน `SequentialValueTree` ดังนั้นหากกระบวนการชริงก์ไปจบลงที่เคสซึ่งไม่ทำให้เกิดปัญหาที่ค้นพบอีกต่อไป การเรียก `complicate` ในการนำ `ValueTree` ไปใช้ของ `SequentialValueTree` ก็สามารถพยายามย้อนกลับได้

## เทคโนโลยีที่คล้ายกัน

การรองรับการทดสอบสเตตแมชชีนของ Proptest ได้แรงบันดาลใจอย่างมากจาก eqc_statem ของ Erlang (ดูบทความ [Finding Race Conditions in Erlang with QuickCheck and PULSE](https://smallbone.se/papers/finding-race-conditions.pdf)) โดยมีความแตกต่างที่สำคัญบางประการ ที่เห็นได้ชัดที่สุดคือ:

- ปัจจุบันรองรับเฉพาะกลยุทธ์แบบเรียงลำดับ แต่มีแผนจะเพิ่มกลยุทธ์แบบพร้อมกันในภายหลัง
- ไม่มีตัวแปร "symbolic" เหมือนใน eqc_statem สถานะของสเตตแมชชีนเชิงนามธรรม (อ้างอิง) แยกจากสถานะของระบบที่ทดสอบ
- เงื่อนไขหลังไม่ได้นิยามไว้ในฟังก์ชันของตัวเอง แต่เป็นส่วนหนึ่งของฟังก์ชัน `StateMachineTest::apply`
