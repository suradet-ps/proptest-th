# ความแตกต่างระหว่าง QuickCheck กับ Proptest

QuickCheck และ Proptest มีความคล้ายคลึงกันในหลายมิติ: ทั้งคู่ทำหน้าที่สุ่มสร้างอินพุตส่งให้ฟังก์ชันเพื่อตรวจสอบพร็อพเพอร์ตี และย่อขนาดอินพุต (shrink) ให้เหลือเป็นเคสทดสอบที่เล็กที่สุดเมื่อพบข้อผิดพลาดโดยอัตโนมัติ

ความแตกต่างสำคัญประการเดียวคือ QuickCheck จะสร้างค่าและย่อขนาดโดยผูกติดกับชนิดข้อมูล (type) เพียงอย่างเดียว ขณะที่ Proptest ใช้ออบเจกต์ `Strategy` ที่กำหนดขึ้นอย่างชัดเจน ซึ่งแนวทางของ QuickCheck นั้นมีข้อเสียเปรียบหลายประการเมื่อนำมาเปรียบเทียบกัน:

- QuickCheck กำหนดตัวสร้าง (generator) และตัวย่อขนาด (shrinker) ได้เพียงหนึ่งชุดต่อหนึ่งชนิดข้อมูลเท่านั้น หากคุณต้องการกลยุทธ์การสร้างข้อมูลที่ต่างออกไป คุณจำเป็นต้องสร้างชนิดข้อมูลใหม่มาครอบ (newtype pattern) แล้วลงมือเขียน implement เทรตด้วยตนเองทั้งหมด ขณะที่ใน Proptest คุณสามารถสร้างกลยุทธ์ที่แตกต่างกันได้มากเท่าที่ต้องการสำหรับชนิดข้อมูลเดียวกัน และยังมีกลยุทธ์สำเร็จรูปในตัวให้เลือกใช้อีกมากมาย

- ด้วยเหตุผลเดียวกัน QuickCheck จึงมีค่าคอนฟิก "size" เพียงค่าเดียวที่พยายามกำหนดช่วงของค่าที่ถูกสร้าง หากคุณต้องการเลขจำนวนเต็มในช่วง 0 ถึง 100 หนึ่งตัว และช่วง 0 ถึง 1000 อีกหนึ่งตัว คุณก็คงต้องสร้าง newtype ขึ้นมาใหม่อีก แต่ใน Proptest คุณสามารถระบุได้ตรงไปตรงมาทันทีว่าต้องการจำนวนเต็มช่วง `0..100` และช่วง `0..1000`

- ชนิดข้อมูลใน QuickCheck นำมาประกอบกัน (compose) ได้ยาก การจะอิมพลีเมนต์ `Arbitrary` และ `Shrink` ให้กับ struct ใหม่ที่เกิดจากการรวมฟิลด์ธรรมดาเข้าด้วยกัน คุณจะต้องลงมือเขียน implement เทรตทั้งสองเองทั้งหมด รวมถึงต้องเขียนฟังก์ชันแมปไป-กลับสองทิศทางระหว่าง struct กับทูเพิลของฟิลด์ แต่ใน Proptest คุณสามารถสร้างทูเพิลของชิ้นส่วนที่ต้องการ แล้วเรียกใช้ `prop_map` เพื่อแปลงให้อยู่ในรูปของ struct ที่ต้องการได้ทันที โดยขั้นตอนการย่อขนาด (shrinking) จะทำงานให้โดยอัตโนมัติตามชนิดข้อมูลของอินพุต

- เนื่องจาก QuickCheck ไม่สามารถกำหนดเงื่อนไขบังคับ (constraints) ของค่าได้อย่างยืดหยุ่น การสร้างค่าและการย่อขนาดจึงอาจทำให้เกิดการปฏิเสธอินพุต (rejected inputs) ทิ้งไปเป็นจำนวนมาก ขณะที่กลยุทธ์ใน Proptest จะรับรู้ถึงเงื่อนไขพื้นฐานเหล่านี้ตั้งแต่แรก จึงไม่สร้างค่าหรือย่อขนาดไปเป็นค่าที่ละเมิดเงื่อนไขเหล่านั้น

ผู้พัฒนาเฟรมเวิร์ก Hypothesis ได้เขียน[บทความอธิบายประเด็นนี้ไว้อย่างละเอียด](http://hypothesis.works/articles/integrated-shrinking/)

อย่างไรก็ดี สิ่งที่ Proptest ทำแตกต่างออกไปก็มีข้อแลกเปลี่ยน (trade-offs) บางประการเช่นกัน:

- การสร้างข้อมูลที่มีโครงสร้างซับซ้อนใน Proptest อาจทำงานช้ากว่า QuickCheck ได้ถึง 10 เท่า (an order of magnitude) สาเหตุเพราะ QuickCheck ทำการย่อขนาดแบบไร้สถานะ (stateless shrinking) โดยพิจารณาจากค่าผลลัพธ์เพียงอย่างเดียว ขณะที่ Proptest จำเป็นต้องจดจำสถานะและความสัมพันธ์ระหว่างทางทั้งหมด เพื่อให้โมเดลการย่อขนาดที่สมบูรณ์และแม่นยำกว่าสามารถทำงานได้อย่างถูกต้อง
